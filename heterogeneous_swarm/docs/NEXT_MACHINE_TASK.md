# 交给 Ubuntu 端 Codex 的任务说明

复制下面正文，附上实际环境采集结果即可继续。工作目录为本仓库的 `heterogeneous_swarm/`。

---

继续异构无人机群论文的物理引擎适配。请先读 README.md、docs/CODE_AND_PARAMETERS.md、docs/PX4_MIGRATION.md、reproduction/README.md 和 verification/summary.json。原研究是 10 架固定翼、16 架 FPV、20 架四旋翼的 178 s 扫掠—重组—巡检任务；P 冻结为 kc=0.24、kf=0.16，另有 RAS04、MMD19 对照以及三组正式配对初态。以现有包和真实源码为依据，不依赖其他电脑的聊天记录。

先采集本机 Ubuntu、ROS、Gazebo、MAVROS、PX4、模型与插件版本，核对 PX4 本地修改及已有吊运项目的运行方式。仓库记录的历史环境是 Ubuntu 20.04、ROS Noetic、Gazebo Classic 11、PX4 1.13.2，实际安装以现场为准。不要自动升级系统或替换现有 ROS 环境。

为原数值代码建立独立 Python 3.11 环境；ROS 节点沿用自身系统环境。运行 tools/verify_handoff.py，保存哈希、九组控制器入口预检和保存轨迹统计复算结果。原 reproduction/、原始轨迹、冻结参数及论文保持只读；所有改写、运行输出和新证据放新目录。必要时重跑一条原数值模型轨迹，准确区分它与 Gazebo/PX4 验证。

随后开展接口核实，先单多旋翼、再单固定翼。可复用同仓库 ../gazebo_sling/ 的启动、MAVROS连接、状态记录等通用做法，但不要复制吊载动力学、吊运轨迹和载荷配置。P、角色任务、时变形状、成员顺序、KDE及名义反馈先保持不变。

重点检查：

1. 统一 ENU 世界坐标、PX4 各机局部原点、航向与速度单位。MAVROS 与直连 PX4 的坐标转换不同，不进行重复 ENU/NED 转换。
2. 用真实返回状态重算控制器。保留名义参考、保持参考、限幅参考、安全输出、实际飞控输入及实际速度的独立日志，区分重放与闭环。
3. 固定翼不能直接套多旋翼速度话题。根据本机固定版本源码核实可用控制模式；登记速度场到位置/航路、航迹/空速或其他接口的映射及参数，再检验转向、爬升、最小速度和共同巡航后备。不要通过瞬移、直接设置模型位置或强制覆盖速度实现跟踪。
4. 仿真时钟控制任务时刻；0.1 s 名义更新、0.02 s 原安全/执行、0.5 s 指标采样分别保留。Gazebo积分与PX4内部控制频率另行记录。发送心跳不能被耗时的安全搜索阻塞。
5. 原安全证书与代理模型一致性有条件。先量化新执行的偏差与后备可执行性，再决定安全预测如何适配；不把旧 2 m 参数和旧证书直接用于宣称 PX4 安全已证明。

先完成能检查接口正确性的单机和小规模闭环，再根据资源与误差证据扩到原 46 机。小规模检查须注明任务规模改变，不冒称论文正式比较。任务起始为空中非零速度状态，需明确起飞、进入任务状态和任务计时零点。若无法满足旧初态，单独登记实际初态和差异。

本阶段交付：环境/模型版本清单、原包核验结果、可复现启动和停止命令、接口实现、逐层日志与单机验证报告，并判断是否具备原规模闭环条件。接口需要实质新增制导设计或现有资源不足时，给出具体问题和实现代价，不通过调P参数、改任务或删除冲突成员掩盖偏差。
